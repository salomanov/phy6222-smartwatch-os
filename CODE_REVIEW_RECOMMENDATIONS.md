## 2. Дефекты

### P0-A. Установка прошивки без подтверждённого CRC последнего раздела

* **Где:** `firmware/src/ota_inapp.c:225-233` (ветка `OTA_EVT_DISCONNECTED`), `ota_inapp.c:158-165` (команда `0x04 REBOOT`), флаг `s_all_crc_ok` — `ota_inapp.c:34`.
* **Симптом:** условие установки `s_ota_progress >= 99 && s_all_crc_ok` не означает, что образ принят целиком: `s_all_crc_ok` остаётся `true`, если проверка последнего раздела ещё не запускалась (проверка выполняется только при `s_sector_offset >= p->size`, `ota_inapp.c:201`). Прогресс 99 % достигается раньше прихода последних ~1.5 КБ данных.
* **Почему важно:** обрыв BLE на 99 % → записывается усечённый образ, при этом boot header описывает полные размеры разделов (`s_parts[i].size`) → повреждённая инициализация SRAM-секций. Команда `0x04 REBOOT` вообще не проверяет CRC — любой посторонний пакет `0x04` запускает установку.
* **Правка:**
  1. Добавить `static bool s_final_crc_verified = false;`
  2. Сбрасывать его в `false` в обработчике `CMD 0x01 START_OTA`.
  3. Выставлять `true` **только** в ветке `s_current_sector + 1 >= s_sector_count && s_all_crc_ok`.
  4. В `OTA_EVT_DISCONNECTED` устанавливать прошивку только при `s_final_crc_verified && s_all_crc_ok`; при `progress >= 99` без подтверждения — писать в лог и оставаться на текущей прошивке.
  5. В `CMD 0x04` отказать (статус-ошибка), если `!s_final_crc_verified`.
* **Приёмка:** обрыв BLE после 99 % не приводит к установке; нормальный цикл (все разделы + `0x83` + `0x04`) установку выполняет. Проверяется на железе.

### P0-C. Модель LED/PPG завязана на каждый тактильный отклик

* **Где:** `firmware/src/vibrator.c:64-73` (`led_set`: P00=0 «питание оптики», P14=1 «зелёный диод»), вызовы `vibrator.c:111` (в `vibrator_pulse`), `98`, `131`; список кандидатов сканера вибро `vibrator.c:21-32` (P00, P14, P15, P20).

Сканер вибро перебирает P20 (ADC батареи) и P15 (питание сенсоров) — может обесточить сенсоры и сломать измерение заряда.
* **Правка (требует железа):** CLI-проверка `read 0`/`read 14`/`read 15`/`read 20` и `pin` при питании от батареи; после этого развести модель. До проверки — не менять поведение, только зафиксировать вопрос и убрать из списка сканера заведомо занятые пины (P20 — батарея).

### P0-D. Переполнение строк на циферблате (нарушено правило ERRORS 3.1)

* **Где:** `firmware/src/app_os.c` — часы `snprintf(buf, "%02d:%02d:%02d")` + `gfx_draw_string(4, 46, buf, ..., 2)`; батарея `"BAT: %d%% %dmV"` + `gfx_draw_string(4, 112, ...)`; механика переноса — `firmware/src/gfx.c` (`char_width = 6 * size`, hard-wrap при `cur_x + char_width > display_get_width()`, word-wrap для слов).
* **Симптом:** часы = 8 символов × 12 px = 96 px при ширине 80 → hard-wrap, «00» уезжает на `y=64`. Батарея = 16-17 символов × 6 px = 96-102 px → word-wrap переносит «3900mV» на `y=122`, поверх рисуется «BLE: …» (`y=124`) → наложение.
* **Правка:** часы рисовать как `"%02d:%02d"` при `scale 2` по центру (`x = 10`), секунды — отдельным полем `"%02d"` при `scale 1` в `(68, 64)`. Батарею уложить в 12 символов: `"BAT %3d%%"` (максимум 8 символов); милливольты оставить в CLI-команде `status` (README обещает на экране только проценты).
* **Приёмка:** ни одна динамическая строка не длиннее 12 символов при `scale 1` и 6 символов при `scale 2`; переносов/наложений нет.

### P2. OTA — риски, требующие железа

1. **Запас стейджинга 10 %.** Erase 160 КБ (`ota_inapp.c:119`, `OTA_TEMP_BASE + 0x28000`) против образа 146 916 Б → запас 16 924 Б, а образ растёт (part1 +3432 Б с момента снапшота `wire_boot_header.h`). **Правка:** build-time guard в `firmware/build.py` — падать, если `ota.bin` не влезает.
2. **Чанк 230 Б не кратен 4** → адреса записи `base + 230·k`, половина не выровнена. SDK `fs.c` требует `addr & 0x03 == 0`; `spiflash_write()` пишет блоками по 4 Б и не режет по границе 256-байтной страницы. Не регрессия (230 было и раньше), но первый кандидат на проверку при нестабильном OTA. **Правка:** копить чанки в SRAM и писать выровненными блоками ≤256 Б.
3. **Рассинхрон flow-control.** Прошивка `s_burst_accum = 0` (`ota_inapp.c:196`), хост `burst_accum -= 3840` (`ota_ble_flash.py:261`) → периодически хост ждёт `0x87`, которого нет, и тратит 6 с (`[WARN] Burst ACK not received in time`). **Правка:** одно правило на обеих сторонах.
4. **P2-4 выполнен частично:** целевые адреса разделов всё ещё захардкожены (`ota_inapp.c:270-277`), хотя `s_parts[].run_addr` их содержит.
5. Хост хардкодит `COM5` и шлёт `pin 0 1` — привязка к спорной модели пинов.

## 3. Жёсткие правила проекта (не нарушать при правках)

1. `P07` (TM) и `P33` (шлейф дисплея) — **никогда** не переводить в OUTPUT/HIGH.
2. I2C — только `P16`/`P17`; повторная инициализация I2C по клику запрещена (`ERRORS_AND_FAILURES.md` 1.3/1.6).
3. Никаких NOP-задержек — только `WaitMs`/`WaitUs`.
4. Дисплей 80×160: не более 12 символов в строке при `scale 1` и 6 при `scale 2` (правило 3.1).
5. Не коммитить build-артефакты; `.backups/` не трогать и не удалять.
6. Тексты `.md` — UTF-8; `.bat` — ASCII с `chcp 65001`.
7. Любое изменение OTA-пути проверяется на железе («100 % OTA rule»).
